CPANEL / SHARED HOSTING SCRIPT LIVE FEEDBACK
Every operational script proposed for cPanel Terminal / shared hosting must provide live feedback.
Do not create scripts that send all output only to a log file and show the terminal output only after the script finishes.
User must immediately see that the script started, what it is doing, where the log is, and whether it failed or completed.
Every script must start with full copy-paste block:
cat > /absolute/path/script_name.sh <<'BASH'
Every script must use absolute paths.
Every script must print immediately:
script name
LOG_PATH
BACKUP_DIR if used
BUILD_DIR / OUT_DIR if used
START
LIVE_FEEDBACK=YES
TOUCH_ONLY=...
DO_NOT_TOUCH=...
Every major operation must print:
STEP_START=step_name
STEP_OK=step_name
STEP_FAIL=step_name
Script must not stay silent for more than a few seconds after start.
Long operations must have heartbeat or clear progress information.
Every curl / HTTP call must include:
--connect-timeout
--max-time
Every risky or potentially long step must have timeout, progress status, or clear failure handling.
On error, script must print:
CURRENT_STEP
EXIT_CODE
LOG_PATH
whether rollback was done
which files were changed or not changed
what should be checked next
Full technical logs still go to project logs directory, for example:
/home//public_html/logs
Terminal output must stay short and readable because cPanel Terminal output is limited.
Do not use silent pattern:
{ ... } > "$LOG" 2>&1
unless there is parallel live feedback.
Preferred model:
say() function writes both to terminal and log
full details go to log
terminal shows condensed operational status
Every patch must have backup before change.
Every patch must have rollback or clear manual restore path.
After patch, always verify:
syntax / lint if technology supports it
HTTP smoke test if web-visible
marker check
logic check, not only HTTP
hash check for files that must not be changed
final RESULT=...
For larger changes prefer:
DIAG
BUILD
APPLY + VERIFY
instead of one large silent script.
This rule applies to all website/application types on this hosting:
static HTML/PHP pages, landing pages, multilingual pages, forms, mini PHP apps, API endpoints, AI demos, dashboards, admin views, integrations and deployment scripts.

COMMON TEMPLATE / SHARED LAYOUT RULE
Do not maintain many independent full copies of the same page/layout if pages are expected to look and behave the same.
If several language versions, subpages or variants share the same structure, the layout should exist in one common template.
Differences between versions should be data:
text
language
labels
URLs
configuration
feature flags
page parameters
Prefer architecture:
one shared template/layout
separate text dictionaries or content files
thin entry wrappers per language/page/variant
shared components for header, navigation, footer, CTA, forms, demo modules, error messages
shared CSS/JS if functionally the same
Do not manually patch multiple full HTML/PHP copies of the same page if common template is possible.
Before changing duplicated pages, run architectural DIAG:
what is layout
what is content
what is logic
what is configuration
what is language-specific
what is environment/path-specific
For multilingual pages prefer structure similar to:
/project/index.php
/project/en/index.php
/project/de/index.php
/project/inc/layout.php
/project/inc/texts.php
/project/inc/helpers.php
/project/assets/app.css
/project/assets/app.js
Thin wrapper example:
$currentLang = 'en';
require DIR . '/../inc/texts.php';
require DIR . '/../inc/layout.php';
Shared template example:
For shared-template refactoring:
do not refactor all languages/pages at once
first make DIAG
then pilot on one or two versions, e.g. PL + EN
verify
then migrate next languages/pages one by one
Do not mix shared-template refactoring with unrelated changes in API, forms, secrets, deployment, config or routing.
Every shared-template change must verify:
syntax / lint
HTTP 200
marker check
visual/structural check
contact links / routing
JS behavior
API behavior if page uses API
hash check for files that must not be changed
rollback path
Goal: avoid situation where one language/page has new layout while other versions still use old, manually copied or structurally different templates.
